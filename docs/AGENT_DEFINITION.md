# AI 에이전트의 정의와 RELO

작성 2026-11-18. "지금은 AI 에이전트라기보다 웹 앱에 가깝다"는 지적을 받고, 널리 쓰이는 정의를 찾아 우리 코드와 견줬다. 모자란 것은 그날 고쳤고, 아직 모자란 것은 6절에 적었다.
루프의 설계는 [`AGENT_LOOP_PLAN.md`](./AGENT_LOOP_PLAN.md), 코드의 어디가 무엇인지는 [`AGENT_INVENTORY.md`](./AGENT_INVENTORY.md)에 있다.

## 1. 정의

아래는 뜻을 우리말로 옮긴 것이다. 보고서에 그대로 인용하려면 원문을 다시 확인한다.

| 출처 | 에이전트란 | 우리가 눈여겨볼 낱말 |
|---|---|---|
| Russell · Norvig, *Artificial Intelligence: A Modern Approach* | 센서로 환경을 지각하고, 구동기로 그 환경에 작용하는 것 | 지각, **작용** |
| Google, *Agents* 백서 (Wiesinger · Marlow · Vuskovic, 2024-09) | 세상을 관찰하고, 가진 도구로 세상에 작용해서 목표를 이루려는 응용 프로그램. 모델 · 도구 · 오케스트레이션 층으로 이루어진다 | **목표**, 관찰, **작용**, 도구 |
| Anthropic, *Building effective agents* (2024-12) | 워크플로는 LLM과 도구를 미리 정한 코드 경로로 엮은 것이고, 에이전트는 LLM이 자기 과정과 도구 사용을 그때그때 스스로 정하는 것이다. 단계마다 환경에서 실제 결과를 얻고, 확인 지점에서 사람에게 멈추며, 최대 반복 수 같은 정지 조건을 둔다 | **스스로 정함**, 환경의 실제 결과, 사람 확인, 정지 조건 |
| OpenAI, *A practical guide to building agents* (2025) · 개발자 문서 | 사용자를 대신해 일을 스스로 해내는 시스템. LLM이 흐름을 관리하고 판단하며, 도구로 바깥 시스템에 작용하고, 가드레일 안에서 움직인다. 답만 하는 챗봇은 에이전트가 아니다 | **일을 해냄**, 도구, 가드레일 |

## 2. 네 정의가 함께 요구하는 것

| | 요건 | 뜻 |
|---|---|---|
| 1 | 목표 | 버튼 하나의 일이 아니라, 이루려는 것이 주어진다 |
| 2 | 관찰 | 지금 환경이 어떤지 읽는다. 한 일의 결과도 다시 읽는다 |
| 3 | 스스로 정함 | 다음에 무엇을 할지를 코드가 아니라 모델이 그때그때 정한다 |
| 4 | 행동 | 도구로 환경을 실제로 바꾼다. 읽고 말하는 것에서 끝나지 않는다 |
| 5 | 반복과 멈춤 | 결과를 보고 다시 정하기를 되풀이하고, 스스로 멈출 때를 안다. 상한이 있다 |
| 6 | 사람 · 가드레일 | 위험한 일 앞에서 사람에게 멈추고, 정해진 선을 넘지 않는다 |
| 7 | 기억 | 앞에서 한 일과 그 결과를 다음 판단에 쓴다 |

우리 계획 문서(`AGENT_LOOP_PLAN.md` 1절)는 3번 하나만 판정 기준으로 삼았다. 워크플로와 에이전트를 가르는 선으로는 맞지만, 그것만으로는 "분석 버튼을 여러 번 누르는 것"과 구별되지 않는다. 1 · 4 · 7번이 비어 있었다.

## 3. RELO와 견주기

| 요건 | 2026-11-18 낮까지 | 지금 | 어디 |
|---|---|---|---|
| 1 목표 | 없음. 고르는 쪽에 "다음 도구를 골라라"만 줬다 | 건의 목표("EUR 39.90 환불을 받는다" · 교환 · 수리)를 고르는 쪽에 주고, 화면 맨 위에 보여 준다 | `ai/prompts/plan.mjs` `goalOf`, `AgentRunPanel.tsx` |
| 2 관찰 | 저장된 건과 앞 단계의 결과 | 같음. 더해서, 건을 바꾼 뒤에는 건을 다시 읽고 고른다. 2026-11-19부터는 사람이 켜 두면 건에 일이 생겼을 때(신청 · 자료 추가 · 답장 저장) 버튼 없이 스스로 시작한다 | `agent.service.mjs` `advance` · `wake` |
| 3 스스로 정함 | 모델이 도구 3개 가운데 고름 | 모델이 도구 5개 가운데 고름 | `plan.mjs` `AGENT_TOOLS` |
| 4 행동 | **없음.** 도구 셋이 모두 읽기 · 생성이라 실행이 끝나도 건은 그대로였다 | 건을 바꾸는 도구 둘: 주문번호 · 주문일을 자료대로 고치기, 쓴 글을 건에 저장하기 | `agent.service.mjs` `propose` · `act` |
| 5 반복과 멈춤 | 최대 5단계, 같은 선택 차단, 스스로 `done` | 같음. 허락을 기다리며 멈췄다가 답을 받으면 이어 간다 | `agent.service.mjs` `advance` · `decide` |
| 6 사람 · 가드레일 | 동의, 시간당 상한, 서버의 재검사 | 같음. 더해서, 건을 바꾸는 일은 무엇이 바뀌는지 보여 주고 허락을 받은 뒤에만 한다 | `AgentRunPanel.tsx`의 허락 칸, `POST …/ai/agent/:runId/decision` |
| 7 기억 | 없음. 실행마다 처음부터 | 같은 건의 지난 실행 2번(고른 도구, 허락 · 거절, 그때 한 말)을 고르는 쪽에 주고, 화면에도 보여 준다 | `agent-run.repo.mjs` `recentForClaim`, `006_agent_actions.sql` |

한 번의 흐름은 이렇다. 자료를 읽는다 → 주문번호가 저장된 값과 다르다 → "자료대로 고칠까요?"를 묻고 멈춘다 → 허락하면 기존 수정 길로 고친다 → 고쳐진 건을 다시 읽고 글을 쓴다 → "이 글을 저장할까요?"를 묻는다 → 허락하면 저장한다 → "복사해서 직접 보내 주세요"라고 하고 끝낸다.

## 4. 행동을 넣으면서 지킨 것

계획의 둘째 원칙은 "루프는 사건을 저장하지 않는다"였다. 까닭은 루프가 직접 쓰면 기한 저장 차단, 사실 지문, 고칠 수 없는 초안이라는 안전장치 셋을 건너뛰게 된다는 것이었다. 행동을 넣되 그 까닭은 그대로 지켰다.

- **허락 없이는 아무것도 바꾸지 않는다.** 모델이 행동을 고르면 실행은 거기서 멈추고, 답이 올 때까지 건은 그대로다.
- **기존 저장 길만 쓴다.** 허락된 행동은 화면의 저장 버튼이 부르는 것과 같은 서비스(`claims.update`, `drafts.save`)를 거친다. 판 번호 확인, 기한 차단, 사실 지문, 초안 불변이 그대로 걸린다. 묻는 사이에 건이 바뀌었으면 덮어쓰지 않고 실패로 남긴다.
- **값은 모델이 정하지 않는다.** 모델은 "고치자"고만 할 수 있다. 무엇으로 고칠지는 서버가 자료에서 읽은 값이고, 저장할 글은 그 실행에서 쓴 글이다.
- **금액과 통화는 고치지 못한다.** 고칠 수 있는 것은 주문번호와 주문일뿐이다.

## 5. 일부러 에이전트에게 주지 않은 것

정의에 "사용자를 대신해"가 있어도, 아래는 맡기지 않는다. 법 문제(대행으로 보이면 안 된다)와 제품의 원칙 때문이다.

| 하지 않는 것 | 까닭 |
|---|---|
| 쇼핑몰에 보내기 | 글은 고객의 것이고, 고객의 이름으로, 고객이 직접 보낸다. ReLo는 대신 보내거나 대신 이야기하지 않는다 |
| "보냈어요"로 표시하기 | 실제로 보냈는지는 고객만 안다 |
| 답장의 종류 정하기, 약속 금액 적기 | 건의 상태를 움직이는 판단이다 (`reply.service.mjs`의 원칙) |
| 받은 돈 기록하기 | 증빙을 보고 사람이 확인한다 |

그래서 RELO의 에이전트는 "혼자 끝까지 하는 에이전트"가 아니라 **사람이 확인 지점마다 허락하는 에이전트**다. 이것은 정의에서 벗어난 것이 아니라 6번 요건이다.

## 6. 아직 모자란 것

1. **진짜 모델로 재지 못했다.** 2026-11-18에 `npm run agent:branch`를 돌렸지만 Google이 `.env`의 키를 받지 않았다(HTTP 401, 키가 유효하지 않음). 키를 바꾼 뒤 다시 돌려야 한다. 그 전에는 "모델이 상태에 따라 고른다"가 아니라 "고르게 하는 장치가 있다"까지만 말할 수 있다. 시험용 가짜 AI는 정해진 순서로 고른다.
2. **스스로 시작하는 것은 세 가지 일뿐이다.** (2026-11-19에 더함) "스스로 시작하기"를 켜 두면 신청했을 때 · 자료를 올렸을 때 · 답장을 저장했을 때 버튼 없이 시작한다. 처음에는 꺼져 있다. 기한이 다가올 때는 시작하지 않는다(사람에게 알릴 길, 곧 메일을 보내는 일을 따로 정해야 해서 넣지 않았다). 서버가 꺼졌다 켜지면 그 사이에 예약돼 있던 시작은 사라진다.
3. **신청을 채우는 것은 루프가 아니다.** (2026-11-19에 더함) 주문서를 올리고 한 줄을 쓰면 AI가 칸을 채우고 사람은 확인만 한다. 다만 이것은 AI를 두 번 부르는 정해진 순서(주문서 읽기 → 한 줄 읽기)이지, 모델이 다음 일을 고르는 에이전트 실행은 아니다. 빠진 것을 되묻지도 않는다(빈 칸이 있는 단계로 데려다 줄 뿐이다).
4. **도구가 다섯 개뿐이다.** 분쟁 해결 안내와 마감 알림은 규칙이고 에이전트의 도구가 아니다.
5. **기억은 얕다.** 지난 실행의 도구 · 허락 여부 · 한 말만 남기고, 읽은 내용은 남기지 않는다(개인정보를 덜 쌓으려고).
6. **앱에는 2026-11-20에 넣었다.** 웹과 같은 서버 기능을 쓴다(상세의 "AI에게 맡기기" 시트, 스스로 시작하기, 신청의 "AI가 채우기"). 서버에 붙지 못한 체험 모드에서는 보이지 않는다. 앱이 대신 지어내지 않기 때문이다.

## 7. 한 문단으로

RELO의 에이전트는 환불 건 하나의 목표를 받고, 건의 상태와 앞 단계의 결과를 보고 다섯 도구 가운데 다음 것을 모델이 고르며, 서버가 실행한 결과를 다시 보고 고르기를 최대 다섯 번 되풀이한다. 건을 바꾸는 일은 무엇이 바뀌는지 보여 주고 사람이 허락한 뒤에만, 기존 저장 길로 한다. 쇼핑몰에 보내는 일은 하지 않는다. 지난 실행에서 한 일과 사람의 답을 기억한다. 사람이 켜 두면 신청 · 자료 추가 · 답장 저장 때 버튼 없이 스스로 시작하고, 그때도 허락 없이는 건을 바꾸지 않는다. 모델이 실제로 상태에 따라 고르는지는 진짜 모델로 잰 결과가 있어야 말할 수 있고, 아직 없다.
